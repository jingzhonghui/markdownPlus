## 1. 项目概述

### 1.1 项目名称

Markdown+ 编辑器

### 1.2 项目背景

传统的 Markdown 编辑器使用 `.md` 文件格式，图片需要单独存储并管理引用路径。这种方式在文件分享、迁移和版本控制时容易造成图片丢失或链接失效的问题。本项目旨在创建一种类似 Microsoft Word `.docx` 格式的自包含 Markdown 文件格式，将 Markdown 内容和相关资源（如图片）打包存储在单一文件中。

### 1.3 项目目标

- 设计并实现 `.mdx` 自定义文件格式，将 Markdown 内容与图片等资源打包存储
- 开发一款支持 `.mdx` 格式的 Markdown 编辑器
- 提供良好的编辑体验和资源管理能力
- 确保文件的可移植性和完整性

## 2. 文件格式规范 (.mdx)

### 2.1 文件结构

`.mdx` 文件采用 ZIP 压缩包格式存储，内部结构如下：

```
example.mdx (ZIP 压缩包)
├── mdx.json          # 文件元数据和配置信息
├── content.md        # Markdown 内容文件
├── assets/           # 资源文件夹
│   ├── images/       # 图片资源
│   │   ├── image1.png
│   │   └── image2.jpg
│   └── attachments/  # 其他附件（可选）
└── thumbnails/       # 缩略图（可选）
    └── preview.png
```

### 2.2 元数据文件 (mdx.json)

```json
{
  "version": "1.0",
  "created_at": "2026-05-09T10:00:00Z",
  "modified_at": "2026-05-09T12:00:00Z",
  "author": "用户名",
  "title": "文档标题",
  "encoding": "UTF-8",
  "content_file": "content.md",
  "assets": {
    "images": [
      {
        "id": "img_001",
        "filename": "image1.png",
        "path": "assets/images/image1.png",
        "mime_type": "image/png",
        "size": 102400,
        "checksum": "sha256:xxx"
      }
    ]
  },
  "settings": {
    "editor_theme": "default",
    "preview_style": "github"
  }
}
```

### 2.3 内容文件 (content.md)

- 标准 Markdown 格式
- 图片引用使用相对路径：`![描述](assets/images/image1.png)`
- 支持所有标准 Markdown 语法
- 支持扩展语法（如表格、任务列表、数学公式等）

#### 3.2.3 AI 助手（第一版）

- [x] 通过可配置的 OpenAI-Compatible Provider 提供流式对话；模型必须支持 `tools`、`tool_calls` 和多轮工具结果消息
- [x] AI 助手以按需打开、可关闭的独立标签呈现，不混入文件标签的保存和恢复状态
- [x] 模型根据自然语言通过白名单 Tool Calling 按需读取发送消息时的当前文档、选区、消息中明确给出的 HTTPS URL 或 Windows 绝对路径
- [x] Main 从当前消息和历史用户消息独立构建精确授权候选；`read_web_url` 与 `read_local_file` 均逐次审批、只执行一次并在 Main 读取
- [x] 来源读取采用无状态提取和分块结果；本地文件审批预览只显示请求路径、规范路径、类型、大小和原因
- [x] 支持替换当前文档、向当前文档插入内容、创建未保存文档；每次写入均先展示预览并等待用户批准
- [x] 运行时策略强制写操作审批，Prompt 或工具参数无权跳过；批准后仍执行目标、版本和内容摘要冲突检查
- [x] 支持取消运行，并同步取消该运行的待审批请求

**授权与隐私要求**:

- 用户发送的消息，以及读取工具实际取得的文档、选区或来源正文，会发送给用户配置的第三方 Provider；界面必须明确提示此数据流向。
- 当前文档全文不默认拼接到初始请求。只有模型调用对应读取工具时，快照中的正文才作为工具结果发送。
- 模型从自然语言判断是否调用来源工具；Main 只接受用户消息中明确出现且精确匹配的公网 HTTPS URL 或带引号的 Windows 绝对路径，不能任意浏览网络、枚举文件系统或使用模型自行生成的路径。
- API Key 不返回渲染进程，不以明文持久化，不写入日志；日志也不记录完整 Prompt、文档正文或来源正文。

**第一版限制与排除项**:

- 单会话仅允许一个运行；最多 12 个工具步骤；单次工具执行超时 60 秒；审批超时 5 分钟。
- 网页响应上限 5 MB，本地文件上限 50 MB，单份提取文本上限 1,000,000 字符；读取结果按约 10,000 字符分块返回，工具步骤、工具超时和审批超时分别受运行时限制。
- 网页读取仅接受用户消息中明确出现的公网 HTTPS 地址，并对每次 DNS 解析和重定向目标执行内网访问防护；本地读取拒绝目录、链接、变化中的文件和不支持的类型。
- 不支持扫描 PDF OCR，不建设向量数据库或持久化知识库，不提供联网搜索或模型自由浏览网络。
- 不提供模型指定本地路径、任意写盘、文件删除/移动/重命名、Shell 命令、上传或发布工具。

## 4. 技术需求

### 4.1 平台支持

- **桌面端**: Windows 10+, macOS 10.15+, Linux (Ubuntu 20.04+)
- **技术栈建议**:
  - Electron / Tauri（跨平台桌面应用）
  - 或原生开发（Qt / .NET MAUI）

### 4.2 性能需求

- 文件打开时间 < 2秒（文件大小 < 50MB）
- 编辑响应延迟 < 50ms
- 支持大文件编辑（> 10MB Markdown 内容）

### 4.3 安全需求

- 文件完整性校验（SHA256）
- 防止恶意代码执行
- 安全的文件解压和解析
- AI 文档写入由应用运行时审批策略强制控制，不能依赖系统提示词作为权限边界
- AI 写入执行前校验文档目标、`revision` 和 `contentHash`，避免覆盖用户审批期间的新编辑
- AI 网页来源拒绝本机、私有网段、链路本地和云元数据地址，并在重定向后重新校验

## 5. 用户界面需求

### 5.1 界面布局

```
┌─────────────────────────────────────────────────────────┐
│  自定义标题栏（Logo + 菜单 + 快捷按钮 + 主题 + 窗口控制） │
├──────────┬──────────────────────────────────────────────┤
│          │  标签栏（多文件标签 + 关闭按钮 + 修改指示器）    │
│  文件    ├──────────────────────────────────────────────┤
│  浏览器  │      编辑器              │    预览           │
│          │      (Markdown 源码)     │    (HTML 渲染)    │
│          │                          │                   │
├──────────┴──────────────────────────┴───────────────────┤
│  状态栏（字数、文件大小、当前行/列、模式切换、保存状态）    │
└─────────────────────────────────────────────────────────┘
```

**说明**:

- 窗口采用无边框设计（frameless），标题栏为自定义实现
- 编辑器支持三种模式：分屏预览（源码 + 预览）、源码编辑（仅源码）、即时渲染（Typora 风格）
- 侧边栏为文件夹浏览器，可折叠（展开显示文件树，折叠显示图标栏）
- 标签栏支持多文件同时打开，点击切换，关闭时未保存提示
